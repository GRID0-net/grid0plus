# Splatoon 3 CloudSave shape in the working hall captures

Both preserved Nextendo hall captures under `raw/nextendo-hall-20260923T205738Z` and `raw/nextendo-second-20260923T210513Z` contain one `CloudSave/GetSaveRecord` exchange. This note records field names and structure only. It does not reproduce the captured save, player identifiers, values, timestamps, tokens, or protobuf bytes.

The console sends a 42-byte framed request containing a single name, `tenants/current/saveRecords/current`. The server replies with a 16,297-byte framed `SaveRecord`: a resolved account-specific `name`, `create_time`, `update_time`, and a nonempty `save_data` MapValue with 87 top-level keys. The two captures contain **the exact same response record**, including its save data and timestamps. They are not two independent examples from which required initial values can be inferred.

Representative top-level fields: `Identifier`, `UserName`, `Version`, `PlayerRank`, `PlayerRankExp`, `Money`, `WeaponLicense`, `GoldWeaponLicense`, `OnlinePlayPenalty`, `LobbyVersus`, `LobbyCoop`, `Versus`, `Coop`, `Season`, `LastSeason`, `Fest`, `FestRecord`, `FestRegion`, `GameRecordHistory`, `HaveGearHeadMap`, `HaveGearClothesMap`, `HaveGearShoesMap`, and `HaveWeaponMap`. Each is a `nn.npln.common.Value`: scalar, map, or array, not a JSON object assembled by the HTTP gateway.

Several maps explain why a genuinely populated save matters to the game: `LobbyVersus` holds lobby tutorial/first-use flags; `LobbyCoop` holds Salmon Run tutorial flags; `Season` and `LastSeason` contain 21 keys each; `Fest` contains 20; `Coop` contains 18; `OnlinePlayPenalty` contains eight. This is a structural observation, **not** evidence that every key is mandatory for a fresh player. The captured record belongs to an already initialized account.

GRID0+ currently answers an 86-byte named `SaveRecord` with an empty `save_data` map and fresh timestamps on each request. It also acknowledges `WriteSaveRecord` without storing the client's delta. Neither working capture includes `CreateSaveRecord` or `WriteSaveRecord`; they cannot tell us what this console would send to create its own full save. Nextendo's source separately documents a real fresh-account sequence in which a zero-message Get is followed by a client-owned Create, but also documents an already-initialized client that treats the same zero-message response as an existing blank record. Switching GRID0+'s Get response to empty or NotFound without resolving that state is not yet grounded. Persisting any client-provided save remains an independent correctness requirement.
