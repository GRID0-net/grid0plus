# Splatoon 3 hall boundary, 2026-09-24

The 14:53 UTC hardware attempt ran SwitchNet commit `7dbace7` and still showed the in-game communication error. VM nginx and npln logs show a successful NPLN login, first schedule reads, Canola, Locker, one empty `Ugcstore/RunQuery`, then a second schedule refresh at 14:53:28. The client cancelled its long-lived streams at 14:53:31. It never called `Ugcstore/GetDocument` or `GameRecord/InitializeAttributes` in this attempt.

Both preserved working Nextendo captures (`raw/nextendo-hall-20260923T205738Z` and `raw/nextendo-second-20260923T210513Z`) follow the same rough sequence through RunQuery, then call GetDocument about 0.2 seconds after the second schedule refresh. That is the first missing call, so an absent-document response cannot explain this attempt: SwitchNet never gets a chance to send one. The first RunQuery asks for the empty `rewards` collection; SwitchNet's single `read_time` response matches the working empty-query shape. Nextendo's `ugcstore.go` and `ugcstore_runquery.go` show a separate, later gap: nonempty queries must enumerate stored, collection-filtered documents, while SwitchNet currently always answers empty.

The patcher audit found the active NPLN tenant/frontline hosts and all three BCAT hosts routed to SwitchNet. This attempt's successful gRPC sequence proves its NPLN route and TLS patch were active. No BCAT request appeared in the VM's 14:52:30–14:53:45 nginx window. Prelude's own notes caution that a BCAT `304 Not Modified` supplies no content to an empty cache; that may explain missing news, but this trace does not establish it as the hall-entry failure.

A structural decode of the two working save responses is in [splat3-save-shape-2026-09-24.md](splat3-save-shape-2026-09-24.md). The latest SwitchNet trace has **no** `WriteSaveRecord` or `CreateSaveRecord` call. The earlier trace that did call `WriteSaveRecord` ran a different response set. Nextendo documents both a Nintendo fresh-account path (zero-message Get, then client-owned Create) and an already-initialised client that treats zero-message Get as an existing empty record and only sends partial Validate writes. We cannot infer which path this console will take after the schedule corrections, nor can we transplant the working capture's populated save. SwitchNet still discards WriteSaveRecord deltas; that is a real persistence defect, but changing Get to zero-message or NotFound without establishing the client's state would be another guess.

The remaining pre-boundary differences are not all protocol errors. The working account has populated save, locker, artwork, League events, gear rewards, and tuning attributes; SwitchNet's private account does not. The exact attribute values are content, not proof of required protocol defaults. The schedule identifier and ETag relationships are captured protocol facts and have been corrected locally. All three schedule families in the working captures use quoted 24-character ETags; SwitchNet previously sent 40-character unquoted Vs/Season hashes and omitted Coop's ETag entirely. After the local fixes are validated and deployed, one hardware attempt should compare the first post-refresh call, not just the visible error.

## After the schedule correction: 15:31 UTC hardware attempt

On deployed commit `25449ab`, the game displayed “multiplayer maps and modes has been updated!”, then re-entered the hall and showed its in-game communication error. The VM trace advanced past the previous boundary: after RunQuery and the next schedule refresh, it called `Ugcstore/GetDocument` at 15:31:47.670; SwitchNet answered `NotFound`, and the client did not call `GameRecord/InitializeAttributes` before refreshing schedules again. The nginx body length was zero. The log did not record the requested name; the next deployment logs it on an absent read.

The August 24 Prelude commit `650ca4c` fixed an unrelated BCAT delivery failure by redirecting `bcat-list-lp1`, `bcat-data-lp1`, and `bcat-topics-lp1` CDN hosts. SwitchNet NRO already names all three, so this is not a missing host in the current install. The working capture's first two GetDocument calls are populated `GameRecord/.../CoopUserAttribute/Data` and `.../VsUserAttribute/Data`; Nextendo's fresh-account analysis says those documents can be absent when the save itself is genuinely absent and the console creates it. SwitchNet instead announces a named, existing, empty save, then has no attribute documents. That cross-service state remains a plausible cause, not yet confirmed from the missing request name.

The observed official missing-document response is a two-frame NotFound with a relative-path message and `nn.npln.errdetails.NError` detail. SwitchNet already used two frames but a generic message without the detail. The accompanying Ugcstore change aligns that error shape and logs the absent document name. If the next attempt still stops here, the log will distinguish a missing player-attribute document from another absent family and determine whether to pursue a client-owned fresh save or a private, explicitly retargeted captured-save/attribute experiment. No captured save data is committed.

## 15:40 UTC attempt and captured missing-document headers

The next hardware attempt on `85a8865` still showed the map-update prompt and hall communication error. The first failed read was `services/Hammer/users/<player>/UserAttribute/Data`; SwitchNet returned a two-frame, zero-body `NotFound`, and the client made no more document reads. Both preserved working Nextendo captures have this same Hammer document absent with gRPC status 5, so creating a synthetic document would contradict the reference.

The preserved flow metadata does include the gRPC trailers. For a missing `GetDocument`, the working server's opening headers carry `npln-grpc-type: ServerStreaming` followed by `npln-grpc-type: Unary`, plus `content-length: 0`. A populated `GetDocument` carries only `ServerStreaming`. SwitchNet previously sent only `Unary` in both cases. The captured status, relative-path message, NError detail, and zero-body framing were already implemented. The type-header difference is corrected and covered by wire tests; its effect on hardware remains to be measured.

The working capture's boot news request to `bcat-topics-lp1.cdn.nintendo.net` received `304 Not Modified`. VM nginx logged no request to the BCAT topics/list/data hosts during the full 15:38–15:42 UTC window of the failing attempt. The missing news is an observation, but there is no evidence yet that it causes this hall failure; `304` itself supplies no content if the console's cache is empty.
